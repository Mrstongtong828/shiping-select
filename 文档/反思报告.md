# 视频学习资源智能筛选系统反思报告

## 一、项目目标与当前完成度

本项目的目标不是做一个只能展示界面的玩具程序，而是完成一条真实可运行的视频学习资源筛选流水线。按照任务书要求，系统需要输入一个学习主题，例如“PCA 主成分分析”，然后从 B 站和 YouTube 检索候选视频，抓取标题、作者、播放量、点赞数、时长、发布时间、字幕等信息，再调用大语言模型按照教学价值进行结构化评估，最后导出 CSV 表格、JSON 原始数据、Markdown 推荐清单和运行日志。

目前根目录开发版已经具备主线工程结构：`main.py` 负责命令行参数和流程调度，`src/search_bilibili.py` 和 `src/search_youtube.py` 负责平台检索，`src/evaluate.py` 负责 OpenAI 兼容接口的 LLM 评估，`src/exporters.py` 负责 CSV、JSON、Markdown 和日志导出，`src/cache_utils.py` 负责本地缓存，`src/asr_whisper.py` 负责 ASR 兜底。项目还新增了 `app.py` 作为 Streamlit Web UI 入口，让不会命令行的老师也有机会通过浏览器运行筛选任务。

从工程质量看，当前已经建立 `.venv`，安装依赖后可以通过 `python -m pytest`、`ruff check .`、`black --check .` 和 `py_compile`。测试覆盖了数据模型、Prompt 加载、Markdown 中文分层导出、缓存读写、ASR 回填、抖音参考数据转换、平台参数规范化以及新版 YouTube transcript API 兼容性。

## 二、遇到的主要问题

第一个问题是中文乱码。由于仓库经历过资料包上传和多次 Windows 终端读写，部分 README、Prompt、schema 枚举和 Markdown 导出文案出现了 mojibake。这个问题表面上只是显示不美观，但实际会影响大模型评估和答辩展示。例如 `audience` 枚举如果乱码，模型输出即使语义正确，也可能无法通过 Pydantic 校验。当前已把根目录开发版的核心中文文件修复为 UTF-8，并通过测试锁定 Markdown 分层标题。

第二个问题是字幕成功率。任务书要求候选视频字幕获取成功率 ≥80%，但真实平台并不总是提供公开字幕。B 站公开视频可能没有 CC 字幕，匿名接口也未必能拿到字幕；YouTube transcript 又可能因为网络出口或 IP 限制失败。这说明“字幕获取”不能只靠单一路径，必须同时准备平台字幕、缓存、代理说明、ASR 兜底和无字幕降级评估。当前 ASR 兜底代码已经存在，但还缺真实小样本验证，这是后续最关键的验收风险。

第三个问题是 YouTube 依赖版本变化。`youtube-transcript-api` 新版本不再提供旧的 `YouTubeTranscriptApi.list_transcripts(...)` 静态方法，必须改为实例方法 `YouTubeTranscriptApi().list(...)`。这个问题如果只看旧文档或旧代码，很容易在运行时才暴露。当前已经修复并增加了单元测试，避免后续依赖升级又悄悄破坏字幕链路。

第四个问题是抖音平台的工程代价。B 站和 YouTube 至少有相对清晰的 API 或社区库，而抖音网页端依赖浏览器登录、滚动、监听数据包和反爬策略。当前项目没有把抖音作为主力平台，而是把 `douyinpachong-main/` 作为参考爬虫，用 `DOUYIN_SAMPLE_JSON` 将导出的 JSON 接入主流程。这种做法承认了封闭平台的工程代价，也保留了加分项展示空间。

## 三、Prompt 迭代与人工评估

项目的 LLM 评估不是简单问模型“这个视频好不好”，而是要求输出固定 JSON 字段，包括相关性、深度、清晰度、是否有数学推导、是否有代码、适用对象、是否推荐和推荐理由。这样做的好处是下游 CSV 和 Markdown 可以稳定消费，人工复核也更方便。

历史人工对照评估抽样 10 条视频，其中系统与人工一致 8 条，一致率 80%，达到任务书 ≥70% 的要求。不一致的案例主要有两类：一类是无字幕但人工认为讲解清楚的视频，另一类是很短但适合作为科普入门的视频。因此 Prompt 后续加入了“无字幕不直接否定”和“短视频可作为科普入门材料，但理由中需说明局限”的要求。

## 四、工程收获

这次项目最重要的收获是理解“可运行”和“可验收”不是一回事。可运行意味着某个命令能跑出结果；可验收则要求环境可复现、错误可解释、输出可交付、测试可验证、文档可读、答辩能讲清楚。比如 B 站小样本能导出 CSV，并不代表双平台 30 条完整流程已达标；mock 测试能证明 ASR 回填逻辑正确，也不代表真实 Whisper 模型和音频下载已验收。

另一个收获是平台选型很重要。开放 API 平台通常更适合主线功能，封闭平台更适合作为工程代价对比或加分项。抖音并不是不能做，而是它的维护成本、登录依赖和反爬风险都明显高于 B 站和 YouTube。如果一开始把抖音作为主力数据源，项目很可能会被反爬细节拖慢，反而影响核心验收。

## 五、下一步计划

后续最优先的事情是配置 `.env`，填入 `YOUTUBE_API_KEY`、`OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `OPENAI_MODEL`，再运行双平台 30 条完整流程。如果 YouTube transcript 继续失败，需要明确记录网络出口限制，并尝试 ASR 小样本验证。随后要生成正式的 `pca_主成分分析.csv`、`pca_主成分分析.md` 和运行日志，把人工对照表更新为当前版本的结果。最后再进行 Streamlit UI 浏览器验收，录制演示视频，并按现场讲解需要微调已生成的答辩 PPT。
